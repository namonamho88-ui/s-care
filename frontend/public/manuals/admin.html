관리자 매뉴얼

시연 환경 운영·판단 검토·대응 승인·지식 품질 관리

기준일 2026-10-12 · 모든 데이터는 가상입니다.

관리자는 AI 판단·대응·지식 게시와 계정을 관리합니다. 개인 관리자 계정 로그인을 기본으로 사용하며, 관리자 토큰은 첫 계정 생성과 복구용으로만 사용합니다. SSO/MFA는 아직 제공하지 않습니다.

1. 관리자가 책임지는 일

일반 사용자는 장애 등록·전체 분석 조회·본인 담당 장애의 후기 작성을 수행합니다. 관리자는 판단 검토·대응 승인·종료·해결 절차 승인·평가·계정 관리를 수행합니다. 서버가 역할과 현재 담당자를 검사하므로 버튼을 우회해 API를 호출해도 제한됩니다.

첫 접속은 로그인 화면의 ‘관리자 초기 설정’에서 환경에 설정한 관리자 토큰으로 로그인합니다. ‘계정 관리’에서 가상 표시 이름·아이디·관리자 역할·가상 담당자를 지정해 초대 코드를 발급합니다. 로그아웃 후 ‘초대 활성화’에서 자신의 비밀번호를 설정하고 개인 계정으로 이용하세요.

일반 사용자는 같은 화면에서 USER 역할로 초대합니다. 담당자 한 명당 개인 계정 한 개를 연결합니다. 초대 코드는 발급 직후에만 표시되며 24시간 유효합니다. 안전한 경로로 직접 전달하세요. 자동 이메일은 발송되지 않습니다.

초대 재발급은 이전 비밀번호와 모든 세션을 폐기합니다. 비활성화도 기존 세션을 폐기합니다. 화면에서 영향을 확인한 후 적용하세요. 본인 계정의 비활성화·초대 재발급은 차단하며 본인 비밀번호는 ‘내 계정’에서 변경합니다.

AI 분석 후 담당자가 추천 부서의 담당자로 바뀔 수 있습니다. 필요한 경우 장애의 ‘5. 후기 검토·저장’의 ‘제목·담당자 수정’에서 관리자가 담당자를 재배정합니다. 일반 사용자에게 관리자 토큰을 전달하지 마세요.

대시보드에서 바로 시작하기

통합 관제 상단의 큰 접수 버튼부터 선택합니다. 알림 문자가 있으면 ‘문자 붙여넣기’, 문자 없이 이상 현상을 발견했다면 ‘장애 직접 등록’을 누릅니다. 접수 버튼을 여는 것만으로 장애를 생성하지 않습니다.

‘지금 처리할 장애’는 전체 조회 결과에서 종료·승인 거부를 제외하고, 내 확인이 필요한 항목 → 긴급도 → 최근 접수 순으로 표시합니다. 최근 이력이 모두 종료 상태여도 이전 미처리 장애를 찾을 수 있습니다. 각 항목에 현재 단계와 다음 행동을 표시하며, 클릭하면 기존 6단계 처리 화면이 열립니다.

목록은 10건씩 표시합니다. 상태 필터를 바꾸면 1페이지로 돌아가고, 완료·거부된 기록은 ‘전체 이력’에서 찾습니다. 이력 화면에서 지정한 유형·시스템·기간 조건은 대시보드에도 적용되므로 상단의 집계 필터 안내를 확인하세요.

‘운영 현황 펼치기’에서 지표·온톨로지·Agent 상세를 확인합니다. 사용 기술 설명은 화면 하단의 ‘기술별 역할 보기’ 또는 ‘사용 기술’ 메뉴에서 확인합니다. 장애 상세의 단계별 기술·실행 근거도 계속 제공됩니다.

시나리오를 이용한 시연은 처리 목록 아래 ‘시연용 가상 장애 만들기 · 관리자’를 펼칩니다. 실행 모드·Provider·시나리오를 선택한 뒤 ‘가상 장애 발생’을 눌러야 장애가 저장되고 분석이 시작됩니다. 일반 사용자에게는 이 영역이 표시되지 않습니다.

목록 필터와 항목 선택은 조회 기능입니다. 승인·재시도·종료는 상세 화면에서 권한에 맞는 버튼을 눌러야 실행됩니다.

발표용 요약 펼쳐 보기

장애를 열고 현재 단계 안내 아래의 ‘한눈에 보는 장애 대응’을 펼치세요. 발생 현상, 판단 결과, 영향 가능 대상 수와 지금 해야 할 일을 한곳에서 확인합니다.

가상 복구 검증 기록이 있으면 오류율·응답 시간·연결 시스템 상태의 조치 전후 값을 보여줍니다. 기록이 없거나 형식이 맞지 않으면 결과를 추정하지 않습니다. AI 분류 결과는 확정된 원인이 아니며, 판단 출처에서 실제 AI·모의 실행 여부를 확인하세요.

요약을 펼쳐 보는 것만으로 승인·저장·복구가 실행되지는 않습니다. 시스템 영향도는 연결 관계 분석, 해결 지식은 승인된 해결 절차, 안전 점검·평가는 AI 판단과 실행 규칙을 확인하는 메뉴입니다.

기술과 모델이 사용되는 지점 확인

왼쪽 ‘사용 기술’ 메뉴에서 6단계 기술 지도와 기술별 사용 지점·역할 표를 확인합니다. 각 업무 화면 하단의 ‘기술별 역할 보기’로도 이동할 수 있습니다. 일반 사용자와 관리자 모두 조회할 수 있습니다.

장애 상세 화면은 각 단계의 관련 기술을 표시합니다. ‘역할과 이 장애의 실행 근거 보기’를 펼치면 해당 장애에 저장된 Provider, 응답 모델, 실제 AI/Mock, 연결 실패 대체 사유, 그래프 엔진과 Agent 실행 기록을 확인합니다. 예정된 단계에는 실행 기록이 없을 수 있으며 이를 완료로 표시하지 않습니다.

Jev는 장애 유형·긴급도·담당 부서와 원인 후보 판단, Ontology는 의존 관계 영향 분석, A2A는 Agent 통신, Hermes는 승인 지식 검색과 해결 절차 초안을 담당합니다. Harness는 전 과정의 근거 검증·승인·실행 통제, MCP는 승인 후 가상 조치·지표 검증, PostgreSQL은 이력과 지식 저장을 맡습니다.

A2A의 6개 Agent가 모두 독립적인 LLM은 아닙니다. Diagnosis는 Jev, Knowledge는 Hermes를 사용하고 다른 Agent는 계획·그래프 결과·승인 지식·보고서를 내부 로직으로 구성합니다. 실제/Mock 판별은 선택한 실행 모드나 연결 배지가 아닌 각 응답의 기록을 기준으로 합니다.

Hermes의 응답 모델이 hermes-agent이면 서버 별칭입니다. 내부 OpenAI 모델명까지 확인된 것은 아닙니다. 지식 검색과 해결 절차 초안은 각각 실패·모의 판단으로 대체될 수 있어 따로 표시합니다. 해결 절차 승인·파일 게시 상태는 해결 지식에서 확인합니다.

문자 붙여넣기로 장애 등록

상단 ‘문자 붙여넣기’에서 배치 알림 또는 TMS 오류율 알림 한 건을 붙여넣습니다. 휴대폰에서도 같은 화면을 이용합니다. 휴대폰 자동 수신 기능은 포함하지 않습니다. 가상·비식별 문자만 입력하세요.

  1. ‘내용 분석’을 누르면 서버 규칙으로 항목을 추출합니다. 이때는 DB에 장애를 만들거나 AI를 호출하지 않습니다. 화면의 가상 예시로 연습할 수 있습니다.
  2. END_OK는 정상 종료로 표시하며 장애 등록에서 제외합니다. ABEND는 비정상 종료, DELAY_END는 종료 지연, TMS는 현재 오류율의 임계치 초과 여부를 확인합니다. 지원하지 않는 형식이나 누락·잘못된 값은 오류로 안내합니다.
  3. 추출한 배치/IF 코드와 관측값을 확인하고 대상 구성요소를 선택합니다. 처음 입력한 코드는 자동 배정하지 않습니다. 같은 코드로 이전에 확인한 구성요소가 하나이면 추천하지만, 등록 전 다시 확인하세요.
  4. 실제 AI 모드 또는 시연 모드 · 모의 판단을 선택하고 ‘등록 & 분석 시작’을 누릅니다. 저장 후 기존 6단계 처리 화면으로 이동합니다. 판단 근거가 부족하면 2단계에서 관리자 확인을 기다립니다.
  5. 같은 알림을 다시 붙여넣으면 기존 장애를 엽니다. 요청 오류가 나도 입력은 유지되며 같은 문자 재요청은 중복 저장을 방지합니다.
DELAY_END의 HH:mm은 종료기한이며 발생일시가 아닙니다. 업무일자·문자 발생일시(KST)·서버 등록 시각은 구분합니다. 생략된 배치명은 추정하지 않습니다. TMS 오류율 95.65%와 임계치 95%의 차이는 0.65%p입니다. 수신자 이름과 발신 기관명·원문 전체는 저장/AI 입력에서 제외하지만, 자유 텍스트에 포함된 개인정보까지 자동 익명화하는 기능은 아닙니다.

목록을 10건씩 보기

장애 이력, 해결 절차, 대응 매뉴얼, Harness 평가, 감사 로그, 등록 계정은 한 페이지에 최대 10건씩 표시합니다. 목록 상단과 하단의 처음·이전·페이지 번호·다음·마지막 버튼으로 이동하세요. 총 건수, 현재 표시 범위와 페이지 번호를 함께 표시합니다.

장애 제목/ID 검색이나 유형·시스템·기간 필터를 바꾸면 1페이지로 돌아갑니다. 각 목록의 페이지는 독립적으로 움직이며, 하단에서 페이지를 바꾸면 해당 목록 위로 이동합니다.

평가와 감사 로그는 서버에서 10건씩 조회하므로 오래된 기록도 마지막 페이지까지 볼 수 있습니다. 페이지 조회 실패 시 기존 결과와 오류가 표시되며 다시 조회할 수 있습니다. 새 평가를 실행하면 1페이지에서 진행 상황을 확인합니다. 일반 사용자의 조회·승인 권한은 바뀌지 않습니다.

2. 시연 전 점검 순서

  1. Vercel 시연 주소에 로그인하고 ‘API 연결’, ‘POSTGRESQL’, ‘NEO4J’ 표시를 확인합니다.
  2. Railway에서 backend·jevos·hermes·neo4j가 정상 실행 중인지 확인합니다. Trial 만료·잔여 크레딧·메모리 한도는 Railway에서 확인합니다. 최종 결제는 프로젝트 소유자가 진행합니다.
  3. ‘해결 지식’에서 Hermes API 상태와 승인된 해결 절차의 게시 상태를 확인합니다. 최근 LLM 미검증은 새 호출 전 또는 backend 재시작 직후에도 표시될 수 있습니다.
  4. 기존 진행 중 장애를 확인합니다. 다른 사용자의 승인 대기를 검토 없이 닫거나 승인하지 않습니다. 최대 활성 장애는 4건입니다.
  5. 발표 전에 별도 가상 장애 하나로 시연 모드 흐름을 연습합니다. 실제 AI 시연은 Local Jev와 Hermes/OpenAI 연결을 각각 확인합니다.
  6. 실제 서비스 키가 없거나 연결에 문제가 있으면 시연 모드를 명확하게 선택합니다. 화면의 Mock 결과를 실제 모델 결과로 소개하지 않습니다.

3. 판단 검토와 대응 승인은 다른 단계

장애를 등록하거나 열면 전용 처리 화면이 열립니다. 상단 스텝퍼의 6개 탭은 접수 → 분석·판단 확인 → 대응 승인 → 복구 검증 → 후기 검토·저장 → 장애 종료입니다. 노란색은 실제 현재 단계, 테두리는 보고 있는 탭, 체크는 완료를 뜻합니다. 메인 화면의 운영 지표·그래프·Agent 현황은 ‘운영 현황 펼치기’로 확인합니다.

2단계에서 확인 근거, 3단계에서 승인·거부 사유, 5단계에서 후기·재발 방지 대책을 작성합니다. 성공 후 다음 단계가 준비되면 해당 입력 화면으로 자동 이동합니다. 실패 시 입력을 보존하며, 처리 결과가 불명확하면 중복 실행 전에 ‘상태 다시 확인’을 누르세요.

전체 처리 %는 완료 단계 수를 기준으로 표시합니다(1/6 = 17%, 3/6 = 50%, 5/6 = 83%). 단일 요청의 남은 시간은 추정하지 않습니다. 제목·담당자 수정은 5단계의 접힌 영역, 실행 기록과 감사 로그는 각 단계 하단의 접힌 영역에 있습니다. 최종 종료는 6단계에서 저장된 내용을 확인한 뒤 직접 실행합니다.

  1. 2단계의 관측과 AI 판단 요약을 대조합니다. ‘AI 판단·원인 후보·처리 근거 더보기’를 펼치면 Jev·Diagnosis·Agent 결과를 볼 수 있습니다. 3단계에서는 영향 자산과 그래프를 확인합니다.
  2. ‘판단 확인’이면 부족한 근거와 불일치 사유를 읽습니다. 필요한 경우 유형·심각도·부서를 고치고 관측에 근거한 확인 사유를 입력합니다.
  3. ‘판단 확정 & 분석 계속’을 누르면 분석이 재개됩니다. 이 버튼은 복구 승인이 아닙니다. 독립 원인 분석의 근거가 부족하면 다시 확인 단계가 생길 수 있습니다.
  4. ‘승인 대기’이면 복구 가이드와 영향 범위를 확인하고 ‘승인 / 거부 사유’를 작성합니다. 승인 또는 거부를 선택합니다.
  5. 승인 후 가상 지표 변경과 별도 검증이 진행되는지 확인합니다. 검증 전 정상 복구를 단정하지 않습니다.
  6. 복구 완료 후 후기·재발 방지 대책을 저장하고 종료합니다. 타임라인과 감사 로그에는 검토 및 승인 증적이 남습니다.
예시 확인 근거: ‘CPU 96%, 메모리 고갈, 서비스 불가 관측을 확인했습니다. 자원 포화는 원인 후보로 유지하며 가상 복구 지표만 검증합니다.’ 관측에 없는 사실을 만들어 승인하지 마세요.

4. 해결 절차 초안 검토·승인·게시

실제 검증 사례: Hermes가 ‘최근 7일간 반복’을 ‘향후 7일간 반복’으로 잘못 작성했습니다. 관리자가 거부했고 Hermes 카탈로그에도 게시되지 않았습니다. 이는 사람의 내용 검토 사례이며 자동 의미 검증이 모든 오류를 잡는다는 뜻이 아닙니다.

‘승인 지식 동기화’는 이미 승인된 Skill만 최대 5개씩 게시합니다. 미승인 초안을 자동 승인하거나 모델을 다시 학습시키는 기능이 아닙니다.

  1. ‘해결 지식’에서 승인 대기 카드를 찾습니다. 실제 Hermes 모델 생성인지 시뮬레이션/고정 지식인지 출처를 확인합니다.
  2. 적용 조건의 수치·기간·시스템, 점검 절차, 해결 방법, 주의사항을 장애 관측·승인·복구 결과와 대조합니다.
  3. 정확한 초안만 ‘해결 절차 승인’을 누릅니다. 승인된 원본은 PostgreSQL에서 검색에 쓰이고, 설정된 Hermes bridge로 파일 게시를 시도합니다.
  4. ‘Hermes Skill 파일 게시됨’과 감사 로그의 SKILL_EXPORTED를 확인합니다. ‘게시 실패’이면 서버/볼륨/인증 설정을 복구한 후 ‘승인 지식 동기화’를 누릅니다.
  5. 잘못된 초안은 ‘거부’를 누릅니다. 거부된 지식은 검색·파일 게시 대상이 아닙니다. 현재 UI에서는 거부 취소나 초안 수정·재생성을 제공하지 않습니다.

5. Harness 평가와 감사 로그

‘모의 판단 50건 평가’는 규칙 기반 시연의 재현성을, ‘Local Jev 50건 평가’는 실제 로컬 모델 분류를 확인합니다. 유형·심각도·부서·재발 4개 필드가 모두 맞아야 한 건이 일치로 집계됩니다.

COMPLETED는 평가 실행 완료입니다. 100% 정답을 뜻하지 않습니다. 검토 수·fallback 수·개별 실제 결과와 정답을 함께 읽으세요. FAILED이면 저장된 오류를 확인한 뒤 연결 문제를 해결합니다.

2026-10-10 클라우드 실제 평가에서는 47/50(94%), 모의 판단으로 대체 0건을 확인했습니다. 이 수치는 고정 가상 분류 벤치마크이며 실운영 성능 보증이나 Hermes 생성 품질 점수가 아닙니다.

감사 로그에서 CREATE, DECISION, REVIEW_DECISION, POLICY_VALIDATED, 승인, MCP 실행, CLOSE, SKILL_APPROVED/REJECTED/EXPORTED 등을 확인합니다. 화면에는 최신 300건이 표시됩니다. 개인 계정의 actor는 USR- 계정 ID이며, 초기 설정 토큰은 bootstrap-admin입니다. 이전 기록의 admin은 과거 공통 토큰 주체입니다. 계정 생성·활성화·로그인·비활성화·재발급도 기록됩니다.

6. 환경과 설정 위치

이 PC의 cloud 설정은 Git에서 제외된 .env.cloud, OpenAI 키는 .env에 저장합니다. 파일을 바꾸는 것만으로 이미 배포된 Railway 환경변수가 자동 갱신되지는 않습니다. 적용 대상 서비스의 Variables 수정과 재배포가 필요합니다.

Vercel에는 DB 비밀번호·OpenAI 키를 넣지 않습니다. 브라우저에는 HttpOnly·SameSite 쿠키로 로그인 세션을 보관합니다. 개인 세션은 8시간 후 만료되며 DB에는 세션 해시만 저장합니다. Supabase의 brain schema를 공개 Data API에 노출하지 않습니다.

TypeSafe는 키가 없어 실제 호출을 검증하지 않았습니다. 향후 TYPESAFE_API_KEY를 backend에 설정하면 선택할 수 있는 Provider 구조만 마련돼 있습니다. 모델·API 제공자 변경 후에는 별도로 재검증하세요.

자세한 실행·이전 명령은 저장소 docs/DEPLOYMENT.md를 따릅니다. 키·비밀번호를 매뉴얼이나 화면 공유에 포함하지 않습니다.

7. 배포·재시작·장애 대응

  1. 배포 전 활성 장애와 RUNNING 평가가 없는지 확인합니다. 현재 backend는 단일 replica로 운영합니다.

8. 운영 범위와 발표 체크리스트

현재는 가상 데이터 기반 기능 시연 환경입니다. SSO·MFA·고가용성·작업 큐 기반 다중 backend·지속 부하 검증·공식 프로토콜 적합성 인증은 포함하지 않습니다.

A2A 0.3.0 JSON-RPC와 MCP 2025-03-26 stateless HTTP의 문서화된 프로필을 사용합니다. 앱 내부 실제 HTTP 왕복 검증과 전체 규격 인증을 구분하세요.

최초 seed는 업무 시스템 12개, 구성요소 40개, 담당자 15명, 장애 200건, 매뉴얼 30개, Skill 20개, 의존 관계 80개, 평가 시나리오 50개입니다. 이후 시연·평가로 기록 수가 증가합니다.

  1. 최종 시연 전 Railway 요금제·자원 한도를 확인하고 동일 환경에서 부하 리허설을 합니다.
  2. 실제 AI와 Mock 결과를 명확히 소개하고 실제 운영 시스템 변경은 없음을 설명합니다.
  3. 온톨로지 전체화면·담당자 검토·대응 승인·보고서·Skill 검토까지 발표 흐름을 연습합니다.
  4. 마지막에 Supabase 저장과 재시작 보존 증적을 확인합니다. DB 백업은 비공개로 관리합니다.

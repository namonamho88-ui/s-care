# AI Incident Brain 3.0 — 관리자 매뉴얼

시연 환경 운영·판단 검토·대응 승인·지식 품질 관리

기준일: 2026-10-11. 모든 데이터는 가상입니다.

관리자는 AI 판단·대응·지식 게시와 계정을 관리합니다. 개인 관리자 계정 로그인을 기본으로 사용하며, 관리자 토큰은 첫 계정 생성과 복구용으로만 사용합니다. SSO/MFA는 아직 제공하지 않습니다.

## 1. 관리자가 책임지는 일

일반 사용자는 장애 등록·전체 분석 조회·본인 담당 장애의 후기 작성을 수행합니다. 관리자는 판단 검토·대응 승인·종료·Skill 승인·평가·계정 관리를 수행합니다. 서버가 역할과 현재 담당자를 검사하므로 버튼을 우회해 API를 호출해도 제한됩니다.

첫 접속은 로그인 화면의 ‘관리자 초기 설정’에서 환경에 설정한 관리자 토큰으로 로그인합니다. ‘계정 관리’에서 가상 표시 이름·아이디·관리자 역할·가상 담당자를 지정해 초대 코드를 발급합니다. 로그아웃 후 ‘초대 활성화’에서 자신의 비밀번호를 설정하고 개인 계정으로 이용하세요.

일반 사용자는 같은 화면에서 USER 역할로 초대합니다. 담당자 한 명당 개인 계정 한 개를 연결합니다. 초대 코드는 발급 직후에만 표시되며 24시간 유효합니다. 안전한 경로로 직접 전달하세요. 자동 이메일은 발송되지 않습니다.

초대 재발급은 이전 비밀번호와 모든 세션을 폐기합니다. 비활성화도 기존 세션을 폐기합니다. 화면에서 영향을 확인한 후 적용하세요. 본인 계정의 비활성화·초대 재발급은 차단하며 본인 비밀번호는 ‘내 계정’에서 변경합니다.

AI 분석 후 담당자가 추천 부서의 담당자로 바뀔 수 있습니다. 필요한 경우 장애의 ‘후기 & 보고서’에서 관리자가 담당자를 재배정합니다. 일반 사용자에게 관리자 토큰을 전달하지 마세요.

| 기능 | 관리자 확인 사항 |
| --- | --- |
| Jev | Provider, 실제/Mock, 유형·심각도·부서·재발, 신뢰도·근거 |
| Ontology | 발생 자산과 역방향 의존 영향 범위 |
| A2A | 여섯 Agent의 실행 상태와 요청/응답 |
| Hermes | 승인 지식 검색 결과와 새 초안의 내용 정확성 |
| Harness | 검토·승인·허용 도구·실패 재시도·감사 증적 |
| 이력/보고서 | 복구 검증 결과, 조치 후기·예방 대책, 최종 종료 |

## 2. 시연 전 점검 순서

1. Vercel 시연 주소에 로그인하고 ‘API 연결’, ‘POSTGRESQL’, ‘NEO4J’ 표시를 확인합니다.
2. Railway에서 backend·jevos·hermes·neo4j가 정상 실행 중인지 확인합니다. Trial 만료·잔여 크레딧·메모리 한도는 Railway에서 확인합니다. 최종 결제는 프로젝트 소유자가 진행합니다.
3. ‘지식 & Skill’에서 Hermes API 상태와 승인 Skill의 게시 상태를 확인합니다. 최근 LLM 미검증은 새 호출 전 또는 backend 재시작 직후에도 표시될 수 있습니다.
4. 기존 진행 중 장애를 확인합니다. 다른 사용자의 승인 대기를 검토 없이 닫거나 승인하지 않습니다. 최대 활성 장애는 4건입니다.
5. 발표 전에 별도 가상 장애 하나로 시연 모드 흐름을 연습합니다. 실제 AI 시연은 Local Jev와 Hermes/OpenAI 연결을 각각 확인합니다.
6. 실제 서비스 키가 없거나 연결에 문제가 있으면 시연 모드를 명확하게 선택합니다. 화면의 Mock 결과를 실제 모델 결과로 소개하지 않습니다.

## 3. 판단 검토와 대응 승인은 다른 단계

통합 관제와 장애 상세의 ‘장애 처리 길잡이’에 접수 → 분석·판단 확인 → 대응 승인 → 복구 검증 → 후기 검토·저장 → 장애 종료의 6단계가 표시됩니다. 체크 표시는 완료, 번호와 ‘현재 단계’ 표시는 지금 진행할 위치입니다. 자동 단계는 기다리고, 노란 안내가 나오면 역할에 맞는 확인·저장을 진행합니다.

현재 단계 안내는 상세 상단에 고정되어 있습니다. ‘판단 확인 위치로 이동’ 또는 ‘대응 승인 위치로 이동’을 누르고 강조된 영역의 순서를 따르세요. 확인 근거나 사유를 입력해야 실행 버튼이 활성화됩니다. 근거가 새로 부족하면 2단계 판단 확인이 다시 나타날 수 있습니다.

5단계에서 후기·예방 대책을 검토하고 저장하면 6단계 최종 확인 안내로 바뀝니다. 저장된 내용을 읽은 후 직접 ‘장애 종료’를 누르세요. Skill 초안 승인은 별도입니다. 오류 시 ‘오류 기록 보기’ → 원인 해결 → ‘원인 해결 후 재시도 위치로 이동’ 순서로 확인합니다.

1. 장애 상세의 ‘판단 & 대응’에서 원본 관측, Jev 분류, Diagnosis 원인 후보, 영향 자산, Knowledge 결과를 확인합니다.
2. ‘판단 확인’이면 부족한 근거와 불일치 사유를 읽습니다. 필요한 경우 유형·심각도·부서를 고치고 관측에 근거한 확인 사유를 입력합니다.
3. ‘판단 확정 & 분석 계속’을 누르면 분석이 재개됩니다. 이 버튼은 복구 승인이 아닙니다. 독립 원인 분석의 근거가 부족하면 다시 확인 단계가 생길 수 있습니다.
4. ‘승인 대기’이면 복구 가이드와 영향 범위를 확인하고 ‘승인 / 거부 사유’를 작성합니다. 승인 또는 거부를 선택합니다.
5. 승인 후 가상 지표 변경과 별도 검증이 진행되는지 확인합니다. 검증 전 정상 복구를 단정하지 않습니다.
6. 복구 완료 후 후기·재발 방지 대책을 저장하고 종료합니다. 타임라인과 감사 로그에는 검토 및 승인 증적이 남습니다.

> 예시 확인 근거: ‘CPU 96%, 메모리 고갈, 서비스 불가 관측을 확인했습니다. 자원 포화는 원인 후보로 유지하며 가상 복구 지표만 검증합니다.’ 관측에 없는 사실을 만들어 승인하지 마세요.

## 4. Skill 초안 검토·승인·게시

실제 검증 사례: Hermes가 ‘최근 7일간 반복’을 ‘향후 7일간 반복’으로 잘못 작성했습니다. 관리자가 거부했고 Hermes 카탈로그에도 게시되지 않았습니다. 이는 사람의 내용 검토 사례이며 자동 의미 검증이 모든 오류를 잡는다는 뜻이 아닙니다.

‘승인 지식 동기화’는 이미 승인된 Skill만 최대 5개씩 게시합니다. 미승인 초안을 자동 승인하거나 모델을 다시 학습시키는 기능이 아닙니다.

1. ‘지식 & Skill’에서 승인 대기 카드를 찾습니다. 실제 Hermes 모델 생성인지 시뮬레이션/고정 지식인지 출처를 확인합니다.
2. 적용 조건의 수치·기간·시스템, 점검 절차, 해결 방법, 주의사항을 장애 관측·승인·복구 결과와 대조합니다.
3. 정확한 초안만 ‘Skill 승인’을 누릅니다. 승인된 원본은 PostgreSQL에서 검색에 쓰이고, 설정된 Hermes bridge로 파일 게시를 시도합니다.
4. ‘Hermes Skill 파일 게시됨’과 감사 로그의 SKILL_EXPORTED를 확인합니다. ‘게시 실패’이면 서버/볼륨/인증 설정을 복구한 후 ‘승인 지식 동기화’를 누릅니다.
5. 잘못된 초안은 ‘거부’를 누릅니다. 거부된 지식은 검색·파일 게시 대상이 아닙니다. 현재 UI에서는 거부 취소나 초안 수정·재생성을 제공하지 않습니다.

## 5. Harness 평가와 감사 로그

‘Mock 50건 평가’는 규칙 기반 시연의 재현성을, ‘Local Jev 50건 평가’는 실제 로컬 모델 분류를 확인합니다. 유형·심각도·부서·재발 4개 필드가 모두 맞아야 한 건이 일치로 집계됩니다.

COMPLETED는 평가 실행 완료입니다. 100% 정답을 뜻하지 않습니다. 검토 수·fallback 수·개별 실제 결과와 정답을 함께 읽으세요. FAILED이면 저장된 오류를 확인한 뒤 연결 문제를 해결합니다.

2026-10-10 클라우드 실제 평가에서는 47/50(94%), Mock 대체 0건을 확인했습니다. 이 수치는 고정 가상 분류 벤치마크이며 실운영 성능 보증이나 Hermes 생성 품질 점수가 아닙니다.

감사 로그에서 CREATE, DECISION, REVIEW_DECISION, POLICY_VALIDATED, 승인, MCP 실행, CLOSE, SKILL_APPROVED/REJECTED/EXPORTED 등을 확인합니다. 화면에는 최신 300건이 표시됩니다. 개인 계정의 actor는 USR- 계정 ID이며, 초기 설정 토큰은 bootstrap-admin입니다. 이전 기록의 admin은 과거 공통 토큰 주체입니다. 계정 생성·활성화·로그인·비활성화·재발급도 기록됩니다.

## 6. 환경과 설정 위치

이 PC의 cloud 설정은 Git에서 제외된 .env.cloud, OpenAI 키는 .env에 저장합니다. 파일을 바꾸는 것만으로 이미 배포된 Railway 환경변수가 자동 갱신되지는 않습니다. 적용 대상 서비스의 Variables 수정과 재배포가 필요합니다.

Vercel에는 DB 비밀번호·OpenAI 키를 넣지 않습니다. 브라우저에는 HttpOnly·SameSite 쿠키로 로그인 세션을 보관합니다. 개인 세션은 8시간 후 만료되며 DB에는 세션 해시만 저장합니다. Supabase의 brain schema를 공개 Data API에 노출하지 않습니다.

TypeSafe는 키가 없어 실제 호출을 검증하지 않았습니다. 향후 TYPESAFE_API_KEY를 backend에 설정하면 선택할 수 있는 Provider 구조만 마련돼 있습니다. 모델·API 제공자 변경 후에는 별도로 재검증하세요.

자세한 실행·이전 명령은 저장소 docs/DEPLOYMENT.md를 따릅니다. 키·비밀번호를 매뉴얼이나 화면 공유에 포함하지 않습니다.

| 구성 | 현재 역할 | 주요 설정 |
| --- | --- | --- |
| Vercel | Next.js 화면과 인증 BFF | Root Directory=frontend, BACKEND_URL, COOKIE_SECURE=true |
| Railway backend | Spring Boot, A2A/MCP/Harness, DB 원본 관리 | ADMIN_TOKEN, cloud 프로필, DB_SCHEMA=brain, DB_URL/USER/PASSWORD |
| Supabase PostgreSQL | 장애·승인·Skill·보고서·평가·감사 저장 | Session pooler 5432, TLS, brain schema |
| Railway jevos | 공식 jevos-v4 CPU 모델 | LOCAL_JEV_URL, LOCAL_JEV_KEY / JEV_API_KEY |
| Railway hermes | 공식 Hermes API와 승인 Skill 파일 | OPENAI_API_KEY, HERMES_API_KEY, 별도 HERMES_PUBLISH_KEY |
| Railway neo4j | 자산 의존 관계와 영향 탐색 | NEO4J_URI, NEO4J_PASSWORD, /data 영구 볼륨 |

## 7. 배포·재시작·장애 대응

1. 배포 전 활성 장애와 RUNNING 평가가 없는지 확인합니다. 현재 backend는 단일 replica로 운영합니다.
2. 환경 변수나 코드를 바꾼 대상만 배포합니다. 진행 중 서버를 재시작하면 자동 이어하기 대신 FAILED로 보존될 수 있습니다.
3. 재시작 후 API/DB/Neo4j, 기존 장애·보고서, 승인 Skill 파일을 확인합니다. Hermes 최근 응답 표시는 새 모델 호출 전까지 미검증으로 바뀔 수 있습니다.
4. Hermes 볼륨을 새로 만들었다면 DB 승인 원본을 기준으로 ‘승인 지식 동기화’를 실행합니다. 원본 DB를 초기화하지 않습니다.
5. 실패 장애는 타임라인 원인을 먼저 해결한 후 ‘실패 작업 재시도’를 누릅니다. 재시도해도 새 근거 부족이면 담당자 확인이 필요합니다.

| 증상 | 확인/조치 |
| --- | --- |
| 전체 API 연결 끊김 | Railway backend 로그, Supabase 연결, Vercel BACKEND_URL 확인 |
| Neo4j UNAVAILABLE | Bolt 연결, 인증, 볼륨 여유 공간과 로그 확인. DB/로그 파일을 임의 삭제하지 않음 |
| LOCAL_JEV → MOCK_FALLBACK | jevos 준비 상태·인증·메모리·실제 오류 사유 확인 |
| MOCK_HERMES_FALLBACK | Hermes/API 키/OpenAI 연결·사용량·응답 스키마 확인 |
| Skill 승인됐지만 게시 실패 | Hermes bridge 연결·별도 인증·볼륨 권한 확인 후 승인 지식 동기화 |
| SSE 재연결 | 일정 시간 후 정상 재연결 가능. 최신 단계가 이어지는지 확인 |
| 복구 후 기록이 사라진 것 같음 | DB/schema/환경 주소와 화면 필터 확인. seed 재초기화 금지 |

## 8. 운영 범위와 발표 체크리스트

현재는 가상 데이터 기반 기능 시연 환경입니다. SSO·MFA·고가용성·작업 큐 기반 다중 backend·지속 부하 검증·공식 프로토콜 적합성 인증은 포함하지 않습니다.

A2A 0.3.0 JSON-RPC와 MCP 2025-03-26 stateless HTTP의 문서화된 프로필을 사용합니다. 앱 내부 실제 HTTP 왕복 검증과 전체 규격 인증을 구분하세요.

최초 seed는 업무 시스템 12개, 구성요소 40개, 담당자 15명, 장애 200건, 매뉴얼 30개, Skill 20개, 의존 관계 80개, 평가 시나리오 50개입니다. 이후 시연·평가로 기록 수가 증가합니다.

1. 최종 시연 전 Railway 요금제·자원 한도를 확인하고 동일 환경에서 부하 리허설을 합니다.
2. 실제 AI와 Mock 결과를 명확히 소개하고 실제 운영 시스템 변경은 없음을 설명합니다.
3. 온톨로지 전체화면·담당자 검토·대응 승인·보고서·Skill 검토까지 발표 흐름을 연습합니다.
4. 마지막에 Supabase 저장과 재시작 보존 증적을 확인합니다. DB 백업은 비공개로 관리합니다.

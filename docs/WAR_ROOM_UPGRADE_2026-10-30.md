## 흐림 원인과 수정

- 기존 scene fog는 거리 40–100에서 적용돼 건물 전체 보기에서 대비를 줄였다. 제거했다. 근거리 흐림 전체를 fog만의 문제로 판단하지 않았다.
- ambient 1.7 + hemisphere 1.5 + directional 2.6과 밝은 파스텔 재질 조합이 과도하게 밝고 낮은 대비를 만들었다. 각각 0.55 / 0.8 / 1.6으로 낮추고 중성 회색·남색 시설 재질을 사용한다.
- 기존 DPR 상한은 1.5, 절전 모드는 1에 안티앨리어싱이 꺼져 있었다. 일반 모드는 최대 2, 절전은 1을 유지하며 안티앨리어싱을 켰다. 고해상도 그림자는 일반 모드에만 적용한다.
- Bloom/Depth of Field 후처리는 기존 코드에 없었다. 제거했다고 주장하지 않는다. ACES tone mapping/exposure 1을 명시했다.
- 기존 `backdrop-filter`는 UI 카드 영역에 적용됐다. 장면 전체의 CSS blur는 없었다. 주요 UI를 불투명하게 바꾸고 backdrop blur를 제거했다. 반투명 창도 불투명 재질로 교체했다.
- 시연 캡처에서 캐릭터 일부가 사각형으로 가려지는 추가 결함을 발견했다. DOM 가림 요소가 없고 캔버스 배경색을 바꾸면 해당 영역 색이 바뀌는 것으로 투명 합성 문제를 분리했다. 설치된 Three r180은 renderer의 `alpha:false`와 별개로 기본 WebGL 컨텍스트를 `alpha:true`로 생성했다. 명시적으로 `alpha:false` WebGL2 컨텍스트를 생성해 renderer에 전달한 시험에서 가림이 사라졌다. 불투명 컨텍스트 속성을 UI 회귀 시험으로 고정한다. 물리 GPU 환경에서 동일 현상이 발생했는지는 미검증이다.
- 바닥/랙 슬롯의 기존 InstancedMesh를 유지했다. 사용자별 색상은 자기 화면과 다른 화면에서 동일한 ID 기반 색상을 사용한다.

## 단계별 동작과 데이터 경계

| 단계 | 장면 동작 | 상태 근거 |
|---|---|---|
| 정상 | 초록 표시등, 패킷 이동, 운영 NPC 순찰 | 현재 서버 스냅샷 또는 명시적 로컬 시연 |
| 장애 | 경고 링, 끊긴 연결, 담당자 이동, 위치 강조 | 장애 노드/명시적 관리자 매핑 |
| 분석 | 분석 콘솔로 이동, 분석 연결선, 모니터 | 서버 분석 단계. 실제 모델 응답/DEMO/fallback 구별 |
| 승인 | 승인 담당자 이동, 노란 콘솔, 복구 대기 | 기존 서버 승인 정책. 역할 선택은 권한이 아님 |
| 복구 | 복구 담당자가 주변 통로로 이동, 도구 작업, 노란 상태, 연결 복원 연출 | 연결 장애의 승인된 RECOVERING 상태. 진행률은 저장된 작업 완료 수/전체 작업 수이며 시간 추정값이 아님 |
| 검증 | 검증 담당자가 콘솔로 이동, 상태 점검 | VERIFY 기록. 실패하면 경고 유지 |
| 완료 | 초록 상태/데이터 흐름, 담당자 복귀 | 승인 + VERIFY COMPLETED + RESOLVED/CLOSED. 지식 자산은 기존 처리 경로 유지 |

DB는 연결 링/의존 링크, 배치는 멈춘 작업 블록/재개 흐름, 서버는 소등/멈춘 팬, 네트워크는 끊긴 선으로 구분한다. 모든 동작은 상태 설명용이며 운영 명령이 아니다.

기존 독립 TwinEngine은 승인 시 계산된 결과를 즉시 확정한다. 그 동작을 변경하거나 실제로 존재하지 않는 복구 소요 시간을 만들지 않았다. 독립 실험의 APPROVED SUCCESS는 완료로, PARTIAL/FAILED/결과 없음은 실패·확인 필요로 표시한다. 연속 7단계 자동 연출은 별도 **로컬 시연**에서 제공한다.

관리자가 기존 장애 ID와 노드를 연결하면 모든 게스트는 같은 제한된 서버 상태를 받는다. 공개 방에는 장애 ID/제목/관측 원문/승인 사유/개인 정보/AI 근거 원문을 전송하지 않는다. 해당 상세는 기존 인증 화면 링크에서 확인한다. 공개 상태는 단계, 노드, 버전, 이벤트 ID, 승인 여부, 완료 작업, 제한된 이력뿐이다. 독립 실험 명령은 장애 연결 중 서버에서 거부한다. 기존 장애 승인 API는 그대로 사용한다.

연결 장애는 활성 방당 최대 1초 간격으로 DB에서 읽는다. 빠르게 끝난 단계가 화면 사이에 생략될 수 있으며, 최신 상태를 늦춰 과거 단계를 현재 처리처럼 표시하지 않는다. 저장된 이력을 볼 수 있고 현재 동작 또는 로컬 시연 단계를 다시 재생할 수 있다. 현재 기능은 서버가 제공하는 노드 상태/의존 연결의 시각화이며 실제 장비의 실시간 지표 수집기를 새로 구현한 것은 아니다.

## 멀티플레이어

기존 원시 WebSocket 서버와 10Hz 방향 입력·서버 충돌 검증을 유지한다. 같은 방의 초기 스냅샷, 입퇴장, 위치/방향은 실제 네트워크로 공유된다. 이동 이벤트는 `run`/장애 revision을 변경하지 않는다. 낮은 revision의 장애 스냅샷은 무시하고, 주기적 sync와 재접속으로 누락 상태를 복구한다.

기존에는 같은 브라우저의 모든 탭이 하나의 `war_guest` 쿠키를 공유해 두 번째 소켓이 거부될 수 있었다. 창별 비밀이 아닌 client ID와 별도 HttpOnly 쿠키로 분리했다. 서로 다른 물리 기기에서 발생한 기존 현상의 원인을 이 코드 문제 하나로 확정하지는 않는다. 같은 층만 보는 모드에서는 다른 층의 사용자가 숨겨지며, 참여자 목록과 건물 전체 보기에서 확인한다.

## 증적, 성능, 배포 경계

원시 실행 로그는 로컬 `work/evidence/`, `work/live-verification.log`, `frontend/war-room-ui-verification.log`, `backend/verification-tests.log`에 있다. 빌드·런타임 파일과 원시 로그는 커밋하지 않는다. 보고서용 화면과 비밀 정보가 없는 운영 검사 요약은 `docs/evidence/war-room-upgrade/`에 보관한다.

로컬 증적: [수정 전](evidence/war-room-upgrade/before-desktop.png), [수정 후](evidence/war-room-upgrade/after-desktop.png), [복구 작업 시연](evidence/war-room-upgrade/war-room-recovery.png), [브라우저 3개 동시 접속](evidence/war-room-upgrade/war-room-three-browsers.png), [모바일 수정 전](evidence/war-room-upgrade/before-mobile.png), [모바일 수정 후](evidence/war-room-upgrade/after-mobile.png).

**남은 그래픽 문제:** 소프트웨어 WebGL의 정지 시연 캡처에서는 큰 투명 가림을 제거한 뒤에도 일부 UI 경계와 캐릭터 주변에 잔상이 남았다. z-index/합성 격리, GPU 합성 비활성화, 프레임 버퍼 보존, MSAA 비활성화를 분리 시험했으나 잔상은 해소되지 않았다. 실험용 스타일과 브라우저 옵션은 최종 코드에서 제거했다. 캡처/드라이버 경로와 실제 표시 문제를 아직 완전히 분리하지 못했으므로 그래픽 최종 완료 판정을 보류한다. 하드웨어 GPU 또는 다른 브라우저 엔진에서 비교 재현이 필요하다. 이 문제를 숨기기 위해 이미지를 보정하지 않았다.

새 서비스의 고정 비용은 없다. 연결 장애 방마다 초당 DB 상태 읽기가 추가되고, WebSocket 송신량 및 브라우저 GPU/CPU 비용은 늘어난다. 기존 Railway JVM 및 Supabase DB를 공유한다. 실제 요금은 요금제·가동 시간·egress·동시 방 수 측정 전에는 확정할 수 없다. REAL AI 호출 비용 구조는 변경하지 않았고 로컬 시연은 AI를 호출하지 않는다.

1차 소켓 10개 시험: 첫 이동 수신 123ms, 이동 구간 2,413ms, 합산 수신 434,394 bytes(연결 초기 스냅샷 제외), 전체 758,713 bytes/284프레임. 같은 이동 패턴을 쉬지 않고 반복하면 약 0.65GB/시간이라는 산식이지만 TLS·운영망·대형 실험 결과·서버 비용을 포함한 청구 추정은 아니다. 연결 장애 poll은 방당 대략 3 SELECT/초이며 전체 활성 방 상한 8개를 유지한다.

소프트웨어 WebGL의 별도 Chromium 3개 첫 측정은 2.51초에 rAF 15회, p95 간격 683ms로 매우 느렸다. 이를 30/60 FPS 달성으로 보고하지 않는다. 필요 시 렌더링과 절전 모드 24Hz/일반 모드 30Hz의 애니메이션 요청 상한을 적용했다. 요청 상한은 실측 FPS 보장이 아니다. 효과 줄이기·시연 일시정지·숨긴 화면에서는 불필요한 주기 렌더링을 멈춘다.

최적화 후 동일한 **효과 줄이기 모드의 정지 장면**에서 2.01초에 rAF 114회, p95 간격 16.8ms를 측정했다. 이것은 UI 프레임 스케줄의 회복을 보여주며 실제 3D 렌더링이 57 FPS라는 의미가 아니다. 실제 서버 3브라우저 기능 시험 시간은 약 3분 → 22.1초로 감소했다. 재측정 소켓 10개는 첫 이동 수신 125ms, 2,411ms 동안 이동 수신 438,627 bytes, 284프레임이었다. 하드웨어 GPU에서 움직이는 사용자 10명과 전체 효과를 함께 켠 성능은 여전히 미검증이다.

불투명 컨텍스트까지 적용한 최종 실제 서버 시험도 2개 모두 통과했다(전체 29.1초). 최종 참고값: rAF 116회/2.00초, p95 16.8ms, 첫 이동 수신 123ms, 이동 수신 437,333 bytes/2,412ms. 원시 로그는 `work/live-verification.log`에 있다.

로컬 개발 검증 당시 미검증: 서로 다른 물리 PC/스마트폰·네트워크, Safari/Firefox, 하드웨어 GPU의 5–10명 렌더링 FPS/발열/메모리, 실제 PostgreSQL/Neo4j와 REAL Jev/Hermes, 운영 WSS 및 비용. 이후 운영 WSS·DB 보존과 CI의 별도 PostgreSQL/Neo4j 검증 결과는 마지막 절에 기록한다. 소켓 10/20개 시험은 10/20개의 실기기 3D 부하 시험이 아니다.

배치 복구 절차는 기존 큐 대리 모델/상태의 시각화다. 파일 파서/재처리 실행 엔진을 새로 만들지 않았다. 원본 자산 → 3D 노드 자동 매핑, 다중 backend instance, 실장비 카메라 충돌 전수 검증은 남아 있다. 현재 명시적 매핑과 단일 backend 배포 조건을 유지한다.

최초 보고 시점에는 운영 배포를 보류했다. 이후 사용자가 남은 문제를 보고받고 운영 배포를 요청했다. 그래픽 잔상 원인 분리와 실기기·부하 검증은 배포 후에도 남은 항목이며, 배포 성공을 그래픽 최종 수용으로 간주하지 않는다.

## 입장 화면·진입 버튼 후속 개선

사용자가 보내 준 모바일 화면은 WebGL 입장 전 로비였다. 이 화면에는 이전 녹색 방사형 그라데이션, 옅은 글자색, 회전·기울이기 transform이 적용된 층별 안내 카드가 남아 있었다. 로비를 밝은 단색 배경, 진한 남색 글자, 변형 없는 흰색 카드로 바꾸고 제목을 ‘3D 장애 대응 워룸’으로 명확히 했다. 모바일 입장 버튼은 입력창 아래 전체 너비로 배치했다. 상단 복귀 링크의 기존 76px 고정 너비로 생긴 글자 잘림도 제거했다.

디지털 트윈 상단의 작은 텍스트 링크는 설명·공간 아이콘·큰 파란색 ‘3D 워룸 입장’ 버튼이 있는 전용 카드로 교체했다. 모바일 버튼 높이는 54px이며 상단에서 바로 보인다.

운영용 빌드 성공. Playwright로 320·390·1280px에서 진입 링크 클릭 → 로비 이동, 게스트 입장 버튼 활성화, 단색 배경·변형 없는 안내, 가로 넘침·상단 글자 잘림 없음, 브라우저 오류 0건을 확인했다. 디지털 트윈 화면 검증은 가상 API fixture를 사용했으며 운영 데이터 수정은 없다. 이 변경은 입장 화면과 진입 버튼에 한정하며, 위 3D 내부 장면의 가림·잔상을 해결했다고 주장하지 않는다.

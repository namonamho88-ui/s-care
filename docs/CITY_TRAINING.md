# 금융도시 지키기 — 퇴근까지 5분

## 범위와 실행

기존 디지털 트윈 → 3D 워룸에서 **금융도시 지키기 · 5분 협동 훈련**으로 진입한다. 직접 주소는 `/war-room/city`이다. 기존 워룸과 장애 접수·분석·관리자 승인·검증·지식 초안 흐름은 유지한다.

운영 반영은 백엔드와 프런트엔드를 순서대로 배포한다. 배포 결과와 운영 주소 검증은 별도 배포 기록에 남긴다. 신규 유료 서비스, 모델 API, DB 마이그레이션은 없다.

배포 순서는 백엔드 → 프런트엔드다. 기존 클라이언트는 새 훈련 프레임을 무시하므로 백엔드를 먼저 갱신할 수 있다. 새 프런트엔드만 먼저 배포하면 훈련 상태를 받지 못한다.

로컬 실행은 기존 `deploy/war-room.env.example` 설정을 재사용한다. Spring 서버와 Next BFF의 `WAR_ROOM_ENABLED=true`, 동일한 `WAR_ROOM_GATEWAY_KEY`, 백엔드의 `WAR_ROOM_ALLOWED_ORIGINS`, 프런트엔드의 `BACKEND_URL`, `WAR_ROOM_WS_URL`이 필요하다. 외부 접속은 HTTPS/WSS를 사용한다. 게이트웨이 키는 브라우저에 노출하지 않는다.

자동 검증:

```powershell
cd backend
.\mvnw.cmd package
cd ../frontend
npm.cmd run build
cd ..
.\scripts\verify-city-live.ps1
# 기존 화면 회귀 검사까지 함께 실행
.\scripts\verify-city-live.ps1 -Regression
```

검증 스크립트는 포트 8087/3100을 사용하며, 임의의 일회성 로컬 키와 H2 메모리 DB로 시작한다. 종료 시 해당 프로세스와 환경변수를 정리한다. 운영·클라우드 DB에 접속하지 않는다.

## 2명 이상 체험 방법

1. 각 브라우저에서 `/war-room/city?room=afterwork`에 접속한다.
2. 서로 다른 닉네임으로 같은 방에 입장한다. 실제 참가자 수와 캐릭터를 확인한다.
3. 한 명이 관제 담당으로 매장·DB를, 다른 사람이 분석 담당으로 서버·네트워크를 조사한다.
4. 각 구역의 **이 구역 조사 → 단서 공유**를 누른다. 역할을 바꾸면 혼자서도 모든 조사를 할 수 있다.
5. 공유 근거 4개를 읽고 후보에 의견을 남긴 뒤 분석 담당이 원인을 판단한다.
6. 복구 담당이 조치를 시험하고 승인 요청한다. 상황 책임자가 훈련 내에서 승인한다.
7. 복구 담당이 실행하고, 관제 담당이 안정화 관측 후 **서비스 정상화 확인**을 누른다.
8. 결과에서 같은 팀으로 다시 도전하거나, 시간 초과 시 자유 연습으로 이어간다.

이동: WASD/방향키, 바닥 선택, 터치 방향 버튼. 주요 구역의 빠른 이동을 사용할 수 있다. 카메라는 전체 도시를 기본으로 보여주며 마우스 회전·줌과 문제 구역 집중 보기를 지원한다.

## 시나리오 모델

모든 데이터는 이 기능을 위해 만든 합성 데이터다. 요청량은 100건/초, 앱 연결 풀 한도는 100개, 장애 원인은 v2.8 앱의 연결 반환 누락이다. DB CPU 32%, 쿼리 p95 18ms, 네트워크 손실 0%는 정상이다. 모델 결과는 무작위로 만들지 않으며 실제 운영 성능을 주장하지 않는다.

| 상태·조치 | 성공률 | 응답 시간 | 대기 | 앱 풀 사용률 | 재발/제약 |
|---|---:|---:|---:|---:|---|
| 장애 | 72% | 4,800ms | 120건 | 100% | 연결 반환 결함 유지 |
| 앱 재시작 | 97% | 800ms | 20건 | 60% | 60초 관측 모델에서 재발 |
| 정상 인스턴스로 우회 | 96% | 1,200ms | 35건 | 100% | 예비 인스턴스 용량은 요청의 80%, 원인 앱 풀은 고갈 유지 |
| 직전 v2.7로 롤백 | 99.95% | 180ms | 0건 | 38% | 연결 반환 결함 제거, 검증 필요 |

실행 연출 8초와 안정화 확인 3초는 서버 시계 기준의 압축 훈련 시간이다. 60초 관측 모델을 실제 60초 운영 점검처럼 표시하지 않는다. 정상화 조건은 성공률 ≥99.9%, 응답 ≤300ms, 대기 0건, 풀 ≤70%, 재발 없음이다. 재시작/우회는 검증에 실패하여 시험 단계로 돌아온다. 승인 전에는 실행되지 않으며 검증 전에는 성공하지 않는다.

## 상태와 인증

- `CityTraining`은 운영 시스템 변경 도구나 기존 장애 승인 API를 호출하지 않는다. `WarRoom`의 동기화된 입력 처리 안에서만 변경된다.
- 훈련 역할은 4개이며 누구나 역할 전환·겸임할 수 있다. 게스트가 실제 `Access.Identity` 또는 ADMIN으로 전환되는 경로는 없다.
- 개인 단서는 해당 연결의 역할로 조사한 뒤 개인화된 훈련 프레임에만 전달한다. 공유된 단서는 발견자와 함께 모두에게 전달한다.
- 중요 요청은 `missionId`와 `revision`을 검사한다. 같은 버전으로 동시 실행된 요청 중 하나만 적용되며, 재시작 전 미션의 늦은 요청은 거부한다.
- 이동은 클라이언트 10Hz, 서버 최대 약 13Hz이며 10Hz 브로드캐스트에서 참가자 상태가 바뀌면 presence 목록을 전송한다. 위치·회전은 기존 아바타의 보간을 재사용한다.
- 훈련 상태는 별도 `training` 프레임이다. 참가자의 이동이 훈련 revision이나 장애 상태를 바꾸지 않는다. 15초 동기화 및 재접속 시 전체 상태를 받는다.
- 서버가 마감 시각을 정한다. 브라우저는 서버 시각 차이를 보정해 표시하고, 시간 초과 결정은 서버에서 한다. 시간 초과 후 자유 연습은 별도 표기한다.
- 배지는 최초 단서·정확한 판단·협업 지원·영향 최소화의 고유 기여로 계산하며 반복 클릭 점수는 없다. 자동 AI 판단/AI 참가자는 구현하지 않았고 표시하지 않는다.

## 참가자 표시와 그래픽 진단

기존 장면은 `player.floor === floor`로 참가자를 숨겼다. 금융도시는 한 층에서 모두 표시한다. 기존 탭별 ID는 일반 탭에서는 분리되지만, 탭 복제나 opener가 있는 새 창에서 sessionStorage가 복사되면 같은 ID를 다시 사용할 가능성이 있었다. Web Locks로 탭 식별자 소유권을 분리하고 HttpOnly 게스트 쿠키와 재접속 방식은 유지한다. 이 원인 후보와 사용자가 겪은 특정 기기의 증상을 동일하다고 단정하지 않는다.

빠른 이동은 다른 캐릭터와 겹치지 않는 인접 위치를 서버에서 선택한다. 캐릭터 이름·역할, 실제 참가자 목록, 도시 고객 NPC를 구분한다.

확인한 기존 렌더러에는 fog, bloom, DOF가 없었다. 따라서 존재하지 않는 효과를 제거했다고 보고하지 않는다. 기존 회청색 배경·바닥, ACES filmic 대비 압축, 저사양 DPR 1, 거리 비례 축소 텍스트가 흐릿한 인상에 영향을 줄 수 있었다. 새 도시는 명시적인 sRGB, NoToneMapping, 불투명 캔버스, 안티앨리어싱, DPR 1~2(저사양 최대 1.5), 밝은 바닥과 네이비 윤곽을 사용한다. 이름은 화면 크기 기준으로 유지하고 UI에 blur/backdrop-filter를 적용하지 않는다. 저사양 모드는 그림자를 끄고 20fps로 렌더링하며 일반 모드는 30fps를 목표로 한다. 움직임 감소는 NPC·패킷 반복 움직임을 줄이되 실제 참가자의 상태 동기화는 유지한다.

발표 시연은 별도 로컬 시간축이며 팀의 승인·배지·결과를 수정하지 않는다. 팀 미션이 진행 중이면 서버의 5분 시계는 계속 흐른다는 안내를 표시한다.

## 운영 제한

- 기존 단일 백엔드 인스턴스 구조를 사용한다. 다중 인스턴스의 공유 저장소/분산 브로드캐스트는 구현하지 않았다.
- 훈련과 게스트 상태는 서버 메모리에 있다. 서버 재시작 시 초기화되고, 모든 참가자가 떠나 2분이 지나면 방이 정리된다. 영구 성적표가 아니다.
- 기본 상한은 기존 워룸과 공유하는 8개 방, 방당 20개 게스트 세션이다. 첫 시나리오는 1~4명 역할 분담에 맞췄다.
- 새로 추가되는 서비스/API 사용료는 없다. 실제 운영 트래픽·호스팅 비용과 물리 기기 GPU 성능은 별도로 측정해야 한다.
- 기존 지식 자산화 기능은 그대로 유지하며, 이 훈련의 결과가 자동으로 실제 지식 저장소에 등록되지는 않는다.

건너뛴 백엔드 검사는 `performanceBenchmark` 옵션이 필요한 반복 성능 벤치마크와 `HERMES_BRIDGE_PYTHON`이 필요한 실제 Python bridge 게시 검사다. 새 훈련은 이 기능들을 호출하지 않는다. 이번 작업에서는 실제 PostgreSQL/Neo4j, 클라우드 WSS, 다중 물리 기기, 하드웨어 GPU 성능, 5~10대 동시 렌더링을 검증하지 않았다. 시간 초과는 서버 모델의 시각 입력으로 검증했으며 브라우저에서 실제 5분을 기다리는 테스트는 실행하지 않았다.
